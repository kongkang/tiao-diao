## 项目：音乐转调微信小程序（新项目启动）

用户需求：小程序内把任意音乐文件转调（升/降半音），尽可能用手机本地算力；用户群为小白与中老年人，界面要极简；变现靠激励视频广告（30 秒）解锁。

### 已确认的技术链路（查微信官方文档核实）
1. `wx.chooseMessageFile({type:'file', extension:[...]})`（2.5.0+）从聊天记录选文件 —— 单文件约 25MB 上限
2. `FileSystemManager.readFile` → ArrayBuffer
3. `wx.createWebAudioContext()`（2.19.0+）→ `decodeAudioData` → `AudioBuffer.getChannelData()` 返回 **Float32Array PCM**（官方文档明确）→ 本地音频编辑可行
4. `wx.createWorker(path, {useExperimentalWorker:true})`（iOS 下 JS 效率提升数倍）+ `WXWebAssembly`（2.13.0+，Worker 内 2.15.0+；只支持加载**包内** .wasm/.wasm.br，不能网络加载或动态编译）
5. WASM 算法：变调用 SoundTouch（LGPL，`setPitchSemiTones` ±12），编码用 LAME → MP3
6. 写 `wx.env.USER_DATA_PATH`（配额 200MB）→ `wx.shareFileMessage`（2.16.1+，需用户点击触发）发回微信

### 关键结论
- 纯端侧 100% 可行，无需服务器。
- 两大硬边界：① 小程序不能读手机本地文件夹，只能从聊天记录选文件（首页必须做三步图示引导）；② 不能直接存进手机存储，只能 shareFileMessage 发回聊天让用户长按保存。
- 性能估算：4 分钟立体声 44.1k，总耗时约 20~45 秒，峰值内存 120~180MB → 需 Int16 管线 + 8 分钟时长上限 + onMemoryWarning 兜底。
- 广告：激励视频需流量主（累计 UV ≥ 1000），首版做成开关默认关，审核期必须关闭。建议做"免费试听 15 秒"再解锁。
- 合规风险：类目避开"音乐"（需网络文化经营许可证），选工具类；定位为本地编辑工具。

### 核实到的 2026 政策（关键）
- **2026-04-01 起**：小程序内售卖虚拟商品（解锁功能/额度）**必须全终端接入官方虚拟支付 `wx.requestVirtualPayment`**（基础库 2.19.2+），禁用 `wx.requestPayment`，不得引导外部支付；否则审核直接驳回。
- **iOS 端走 Apple IAP，中国区最低价格点 ¥1**（1~10 元间每 0.5 元一档）→ **¥0.1~0.8 的小额订单在 iPhone 上发不出去**。
- 虚拟支付价格必须后台预配置道具（productId + goodsPrice，单位分，必须与后台一致，否则 -15013）→ **不支持动态价格**。
- 两种模式：`short_series_goods`（道具直购）/`short_series_coin`（代币充值，兑换比例发布后不可改）。
- 费率：Android/鸿蒙/Windows **1%**（限时优惠，标准 10%）；iOS **12%**（标准 17%，苹果佣金）。
- 开通：类目含「工具」+ 认证 + ICP 备案；个人主体也可开（月限额 10 万）；**必须单独打开"苹果支付"开关**，否则 iOS 下单失败。
- 签名必须服务端算（AppKey、session_key 不能进前端）；发货推送 + 主动查单双通道，按订单号做幂等。

### 因此给出的方案
- 付费形态改为**分钟额度包**：¥1=10分钟 / ¥3=30分钟 / ¥6=60分钟，转歌时按 ceil(分钟) 扣额度 → **单价仍是 0.1 元/分钟**。绕开 iOS ¥1 下限与动态价格限制。
- 首版用**道具直购 + 云数据库自记余额**（比代币模式快、风险小；代币兑换比例不可逆）。
- 需极轻量后端：**微信云开发 CloudBase**（云函数算签名 + 云数据库存余额 + 接发货推送）。音频 PCM 仍全本地处理，只有订单数据上云。
- 广告失败放行状态机：实例创建失败/load 失败/onError/超时 8s → 放行；中途关闭（isEnded=false）→ 不放行；多广告序列中途失败 → 已看的有效，剩余直接放行。可加"每日失败放行次数上限"防刷。
- 收益测算：付费 ¥0.5 到手 Android ≈¥0.495 / iOS ≈¥0.44；2 个广告约 ¥0.06~0.24 → **付费收入是广告的 2~8 倍**，建议付费入口给足曝光。

## 调研：WorkBuddy 小程序自动发布能力 + 发布前准备

用户追问：开发完后 WorkBuddy 能自动完成发布吗？需要提前准备什么？用哪个模型？

### WorkBuddy 发布能力核实（本地技能文档 + 联网交叉验证）
- 本机版本 **5.6.2**，已满足要求（发布能力需 **5.6.1+**）。
- 能力属实：切「代码开发」模式 → 选「小程序」→ 生成后点应用空间右上角**「分享」**按钮进入发布流程。扫码绑定账号 → 上传代码 → 生成体验版 → 提交审核 → 版本发布，**全程在 WorkBuddy 内完成**，无需另装微信开发者工具、无需手动传代码包。
- 三种版本路径（官方原文要点）：
  - **14 天试用版**：无需注册账号，扫码即建，最多 15 人体验，**不能转正式版**。
  - **体验版**：需自有账号，管理员扫码授权，最多 15 名体验成员。
  - **正式版**：提交微信审核，审核通过后发布。
- **重要坑**：同一个 WorkBuddy 应用创建试用版后**不能改绑已有账号**。打算长期运营 → 一开始就绑定自有账号。
- 工具层面：目录含 `project.config.json` / `app.wxss` / `app.json`(带 pages) 即被识别为小程序；返回 `sites_miniprogram_app_created` 且 `deployed:false` 是**正常状态**（第 2 步在用户面板点），不是失败。小程序**无法通过该工具下线**，要去应用面板操作。

### 发布前必须提前准备的（按耗时倒排）
1. **ICP 备案最耗时（7~20 工作日）→ 现在就去办**。自 2023-09-01 起新小程序**必须先备案后上线**，未备案无法提交审核、无法上架。入口：微信公众平台后台首页「去备案」；每日有提交配额限制。域名需实名认证满 3 天。
2. **类目选「工具」**（避开「音乐」，音乐类需网络文化经营许可证）。类目必须与实际功能一致，不得超类目。
3. **开通虚拟支付**：入口 微信公众平台 → 支付与交易 → 虚拟支付。需**已认证 + 已备案 + 类目含工具**。
   - **新变化（推翻此前方案假设）**：**个人主体现在也能开通虚拟支付**了（此前"个人不能卖虚拟商品"已放开）。条件：中国大陆居民身份证 + 已认证 + 已备案 + 类目含工具。**月限额 10 万元（全终端合计）**。超过此量级建议注册个体工商户。
   - 费率：Android/鸿蒙/Windows 主动支付 **1%**（限时优惠，标准 10%）；**iOS 12%**（全是 Apple 佣金，腾讯 5% 技术费限时减免）。iOS 走 Apple IAP，**中国区最低 ¥1**，结算周期 45~60 天。
4. **隐私政策独立页面 + 首启弹窗主动勾选**（2026-04-01 强制）。不得折叠在用户协议末尾。驳回 TOP1 是"主体信息不符"（28.7%），隐私协议问题占 32.1%。
5. **流量主需累计 UV ≥ 1000**，审核期广告必须关闭。
6. **音频不得自动播放**：《小程序运营规范》3.5.2 明确禁止用 setTimeout / triggerEvent / 注入 JS 绕过 autoplay 限制，违规直接驳回。合规路径 = 真实用户触点 + 同步执行 + 资源就绪。你的"试听 15 秒"按钮天然合规，但**不能挂到 onLoad/onShow 自动播**。
7. **包体积**：主包/单分包 ≤2MB，全部 ≤20MB（服务商代开发 ≤30MB）。**SoundTouch + LAME 的 .wasm.br 必须放分包**，主包只留 UI。

### 模型建议（延续上一轮结论）
- 开发 + 发布准备全程仍用 **Kimi-K3**（极致模式 + 高思考强度）；发布阶段的云函数签名代码生成也用它。
- 模型只影响代码产出质量，**不影响发布能力本身**——发布是 WorkBuddy 内置流程，与模型无关。

### 本轮结论要点
用户当前最该做的事 = **今天就去注册小程序账号并启动 ICP 备案**（因为要 7~20 工作日），而不是等开发完。

### 官方 API 复核结果（全部无阻塞）
- `wx.shareFileMessage`（2.16.1+）：参数只有 filePath（须本地路径）/fileName（后缀须与 filePath 一致），**无格式白名单**，mp3/m4a/wav 可发。→ 出口通
- `wx.chooseMessageFile`（2.5.0+，extension 过滤 2.6.0+）：官方未给单文件大小上限（"约 25MB"是保守自设），代码里 24MB 自限没问题
- `WebAudioContext.decodeAudioData(ArrayBuffer, success, error)`：官方文档**没有列格式支持矩阵**（插件不支持）→ flac/aac 在 iOS/Android 的解码成功率仍是 M0 真机实测项，mp3/m4a 大概率稳
- 虚拟支付：价格档位官方文档仍未给出合法值清单 → ¥9.9 档位维持"M0 建道具实测，不合法退 ¥9.5 再退 ¥10"。**新发现成本项：iOS 虚拟支付需苹果 IAP 共享密钥 → 需要 Apple Developer 账号（约 ¥688/年）**，此前方案未计入；可先开 Android 收款，iOS 后补

### 本轮发现并修复的 2 个引擎 bug（重要）
1. **WSOLA 时长守不住**：原 stretch() 的推进公式 `pos = start + SEQ/tempo - OVL` 里 start 含搜索偏移量，每块实际消费被越推越大 → +2 半音时 3 秒歌缩到 2.34 秒。重写为标准写法：名义位置按 `step=(SEQ-OVL)/factor` 严格推进 + 搜索窗以名义位置为中心对称展开（偏移零均值不漂移）。参数语义从 tempo 改为 factor（输出/输入时长比）。
2. **lame.min.js 无 module.exports**（浏览器全局函数写法，结尾 `lamejs();`），Worker 的 CommonJS require 拿到空对象 → `new lame.Mp3Encoder()` 必崩。修复：文件末尾追加 `module.exports = lamejs;`。

### 修复后 Node 验证结果（/tmp/tiao-pitch-test/test.js，自相关测频）
ping/pong PASS；+2 半音时长 2.95s/3.0s PASS、频率 495.5Hz（期望 493.9）PASS；-2 半音 390.3Hz（期望 392.0）PASS；MP3 3s@128kbps=47.6KB 帧同步字合法 PASS；60s 立体声 +3 半音全流程 2.2s（≈27× 实时，Node/Mac 参考值——真机 JS 预计 5~15× 实时，8 分钟歌约 30~90s，若太慢再上 WASM SoundTouch，接口已预留）。
已知小尾巴：输出比输入短约 1.7%（WSOLA 循环尾部截断），音乐上无感，M0 后可补尾部 flush。

**可以继续开发**。平台能力全部无阻塞、引擎算法本体已验证正确、商业化路径（虚拟支付+广告）政策面无硬阻塞。剩余风险全部集中在"只能真机/后台验证"的三件事：decodeAudioData 格式矩阵、真机性能/内存、¥9.9 档位合法性。下一步 = M0 真机 PoC + 并行办理注册/备案/虚拟支付（外部依赖，等审核）。

## v3 内存架构重构轮（10-06 凌晨，用户报"系统内存不足，处理被中断"+提议切片处理）

### 诊断（用户判断正确：不是泄漏是架构浪费）
4MB wma≈4分钟立体声=85MB PCM，旧架构在无 transfer 机型上来回拷 4 趟（解码结果→主线程→再送回 worker→结果包），加 WASM 堆解码后不回缩、WAV 输出 42MB，worker 峰值 ~300MB → onProcessKilled。

### v3 架构（PCM 常驻 Worker，全部落地）
- **PCM 永不跨线程**：文件字节（几 MB）进 Worker，FFmpeg WASM 解码后以 **Int16 常驻 Worker 单槽 STORE**（token 引用）；主线程只收元数据和最终结果包。试听=worker 内切片变调回传 15s 小包
- **解码器统一**：全部格式（wma/mp3/m4a/flac/wav/aac）都走自带 wasm（mp3float+flac+aac+pcm_s16le/f32le+mov/aac/asf/mp3/flac/wav demuxer），不再用系统 decodeAudioData（主线程 2×PCM 峰值也没了）。0.88MB→brotli 0.35MB
- **拉取式 C API**：ff_open/ff_pull/ff_close + ff_duration_sec（预分配依据），wasm 堆有界（≈文件大小）不回缩也无所谓了
- **输出默认 mp3**（lamejs，160kbps）：4 分钟 4.6MB（wav 是 42MB），config.ENCODE='mp3'
- **自愈**：engine.storeHas(token) + audio.ensureSong()——worker 被杀后自动按 path 重新解码，页面无感
- 内存账（4 分钟立体声）：store 42MB(int16) + 每声道 float 中间量 ~170MB 峰值（M1 SoundTouch 流式后消除）；跨线程从 ~340MB 降到 <10MB

### 本轮两个深坑（复用必读）
1. **FFmpeg 解码 EAGAIN 状态机**：mp3/aac 解码器有预缓冲，avcodec_send_packet 会 EAGAIN（包未被消费）。必须 g_pending 暂存包→receive 腾空间→重发同一包；EOF 冲刷 NULL 被 EAGAIN 也要回外层收帧后重发。否则"收不到帧发不进包"死循环（wma 逐包出帧不触发，mp3 必触）
2. **WASI 桩必须写出参**：fd_write(fd,iovs,iovn,nwr) 返回 0 却不写 nwr → musl fprintf 认为短写无限重试 → ffmpeg av_log 第一条日志就卡死整个 wasm。曾误判为"-Oz 优化器 UB"（加 fprintf 就好——其实是测试脚本换了带正确 fd_write 的桩！），排查绕了大弯。clock_time_get/environ_sizes_get/fd_read 同理都要写回出参
